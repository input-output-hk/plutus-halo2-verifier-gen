# `stats` — Verifier Cost Estimation

This module estimates the on-chain cost of a Halo2/KZG verifier without
running the prover.  Two modes exist:

| Mode | Input | Output |
|------|-------|--------|
| **Estimate** | chip list + circuit config | proof size, VK size, verifier op-counts |
| **Exact** | extracted `CircuitRepresentation` | exact op-counts from the real VK |

---

## Module layout

```
stats/
  chips/          — chip definitions (advice/fixed columns, gates, lookups, …)
  arguments/      — permutation, lookup, trashcan argument helpers
  data/           — CircuitConfig, CircuitStatistics
  pcs/            — PCS trait (PcsEstimate) and H2MO concrete impl
  lookup/         — PlookUp / lookup argument estimators
  estimate/       — estimation pipeline (see below)
  compute/        — exact computation from a real VK
  profile.rs      — ChipProfile struct + chip_profile() function
```

---

## Estimation pipeline (`estimate/`)

```
process::<PCS>(pi, ci, config, chips)   [build.rs]
      │
      ▼
  Processed { nb_advice, nb_fixed, nb_copy_constrained,
              circuit_degree, gate_args, lookup_args,
              trashcan_args, nb_advice_fixed_evaluations, … }
      │
      ├─▶ estimate_proof_size::<PCS>(…)   → bytes
      ├─▶ estimate_vk_size::<PCS>(…)      → bytes
      └─▶ estimate_verifier_code::<PCS>(…) → CircuitStatistics
```

`process` merges chip column sets, computes copy-constrained columns
(permutation chunks), and derives the rotation-query map used by the PCS.

## Chip profiles

### What is a `ChipProfile`?

`profile.rs` exposes a lightweight struct that captures the chip-level
parameters needed by the [web cost explorer](../../../docs/cost.html):

```rust
pub struct ChipProfile {
    pub degree:          usize,  // max gate degree required by the chip
    pub advice_cols:     usize,  // total advice columns
    pub fixed_cols:      usize,  // total fixed columns (appears in the VK)
    pub copy_constraints: usize, // copy-constrained columns contributed by this chip
    pub nb_lookup_tables: usize, // number of lookup tables
    pub gates:           usize,  // number of gate argument groups
    pub lookups:         usize,  // number of lookup arguments
    pub trash:           usize,  // number of trashcan arguments
    pub evals:           usize,  // advice + fixed column evaluation queries
    pub gate_ops:        ScalarOps,
    pub lookup_ops:      ScalarOps,
    pub trash_ops:       ScalarOps,
    pub proof_size:      usize,
    pub vk_size:         usize,
}
```

### How `chip_profile` is computed

`chip_profile::<PCS>(chip)` calls `flatten_chips` to resolve chip
dependencies, then reads column counts, gate/lookup/trashcan arguments, and
rotation sets directly from the chip trait — without going through `process`.
`compute_degree` is called with `extra_degree = 0` to get the chip's own
contribution.

### Generating `docs/chip_profiles.json`

The web cost explorer (`docs/cost.html`) loads chip parameters at runtime
from `docs/chip_profiles.json` rather than hardcoding them.  That file is
generated by the `dump_profiles` binary:

```sh
cargo run --bin dump_profiles
```

**Regenerate this file whenever chip column counts, gate degrees, or lookup
counts change.**  Commit the updated JSON alongside the Rust changes.

### Regenerating the WASM bundle

The web cost explorer also depends on the compiled WASM bundle in
`docs/wasm/`.  Regenerate it with:

```sh
wasm-pack build --target web --out-dir docs/wasm
```

CI will fail if `docs/wasm/` is stale relative to the Rust source.

## Supported chips and their flags

| CLI flag | `SupportedChips` variant | Description |
|----------|--------------------------|-------------|
| `--native` | `Native` | Native field arithmetic |
| `--automaton` | `Automaton` | Regular expression parsing (fixed lookup table) |
| `--base64` | `Base64` | Base64 decoding |
| `--sha256` | `Sha256` | SHA256 hash |
| `--sha512` | `Sha512` | SHA512 hash |
| `--poseidon` | `Poseidon` | Poseidon hash |
| `--jubjub` | `EdwardsJubjub` | JubJub ECC (Edwards curve) |
| `--hash-to-curve` | `HashToCurve` | Hash-to-curve (JubJub) |
| `--curve25519` | `Curve25519` | Curve25519 ECC |
| `--bls12-381` | `WeierstrassBls12381` | BLS12-381 ECC (foreign field, 7 limbs) |
| `--secp256k1` | `WeierstrassSecp256k1` | secp256k1 ECC (foreign field, 4 limbs) |
| `--secp256r1` | `WeierstrassSecp256r1` | secp256r1 ECC (foreign field, 4 limbs) |

## Adding a new chip

1. Implement the chip in `chips/primitives/` following the existing pattern
   (advice columns, fixed columns, gates, lookup tables).
2. Add a variant to `SupportedChips` in `chips/mod.rs` and wire it into
   `flatten_chips` / `flatten_tables`.
3. Add a CLI flag in `cli.rs` and map it in `estimate_cost`.
4. Add the chip to the `chips` list in `src/bin/dump_profiles.rs`.
5. Regenerate `docs/chip_profiles.json` and the WASM bundle:
   ```sh
   cargo run --bin dump_profiles
   wasm-pack build --target web --out-dir docs/wasm
   ```
6. Update `docs/chips.html` and `docs/cost.html` with the new chip entry.
